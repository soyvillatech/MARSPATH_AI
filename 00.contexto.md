# MarsPath AI — Contexto del reto y dirección del producto

## 1. Reto de la NASA

El reto **Guía de Supervivencia Interplanetaria: Mapa Marciano** propone crear una vista integrada y por capas de una ubicación o una ruta sobre la superficie de Marte. La herramienta debe reunir datos de varias misiones científicas y ayudar a un explorador humano a planificar un Marswalk seguro, eficiente y científicamente útil.

La prioridad no es construir un mapa decorativo. La prioridad es convertir datos científicos en decisiones de navegación comprensibles:

- ¿Por dónde conviene desplazarse?
- ¿Qué zonas deben evitarse?
- ¿Qué ruta permite alcanzar los objetivos científicos con menor riesgo?
- ¿Cuánta distancia, tiempo y desnivel implica cada alternativa?
- ¿Qué evidencia respalda cada capa y cada decisión?

## 2. Oportunidad del proyecto

Las misiones de Marte han producido imágenes, mapas geológicos, modelos de elevación, observaciones de rovers y otros productos científicos. Sin embargo, esos datos no siempre están organizados para responder a una misión humana localizada.

MarsPath AI será una interfaz de planificación que combine esos datos en una región acotada de **Jezero Crater**. El usuario podrá elegir un origen, un destino y, opcionalmente, varios objetivos científicos. El sistema analizará el terreno y propondrá rutas transitables, explicando sus ventajas y limitaciones.

La aplicación debe distinguir siempre entre:

- **Dato real:** observación, mapa o producto publicado por una misión o institución científica.
- **Cálculo:** resultado obtenido por la aplicación, por ejemplo pendiente, distancia o coste de una ruta.
- **Suposición:** parámetro configurable, por ejemplo velocidad de caminata o pendiente máxima.
- **Simulación:** resultado hipotético, por ejemplo consumo estimado de recursos.

## 3. Objetivo principal

Construir un prototipo frontend funcional que permita planificar y comparar rutas marcianas óptimas sobre una cuadrícula de terreno.

Una ruta óptima no significa siempre la más corta. Significa la mejor alternativa según el objetivo seleccionado y las restricciones de la misión. El sistema debe poder optimizar, como mínimo:

1. **Seguridad:** reducir pendientes, peligros y zonas restringidas.
2. **Tiempo:** reducir la duración estimada manteniendo la transitabilidad.
3. **Ciencia:** visitar objetivos científicos relevantes con un coste razonable.
4. **Equilibrio:** combinar seguridad, tiempo e interés científico mediante pesos configurables.

## 4. Alcance del MVP

El MVP debe priorizar una experiencia completa de planificación de rutas sobre una región pequeña y verificable de Jezero. Debe incluir:

- Mapa 2D navegable.
- Selección interactiva de origen y destino.
- Selección de objetivos científicos intermedios.
- Carga de una cuadrícula de elevación local o preparada previamente.
- Cálculo de pendiente y transitabilidad.
- Zonas de exclusión y peligros identificados como reales o simulados.
- Motor A* para calcular rutas sobre el terreno.
- Tres perfiles de ruta: segura, rápida y científica.
- Comparación de alternativas en un panel de métricas.
- Explicación de por qué una ruta es más conveniente.
- Guardado local de una misión.
- Reporte resumido de la misión.

La visualización 3D con CesiumJS es opcional y posterior. No debe retrasar el funcionamiento del mapa 2D ni del motor de rutas.

## 5. Región de estudio

La primera versión trabajará con una zona delimitada de Jezero Crater, no con todo Marte. La región debe tener:

- DEM disponible y procesable.
- Cobertura cartográfica suficiente.
- Capas geológicas o puntos científicos utilizables.
- Una extensión manejable para que el algoritmo se ejecute en el navegador.

Los límites, la resolución, el sistema de coordenadas y la fecha del producto deben quedar documentados en `terrain-metadata.json`.

## 6. Fuentes y uso correcto

Las fuentes del reto se utilizarán con responsabilidades concretas:

| Fuente | Uso en MarsPath AI | Limitación |
| --- | --- | --- |
| NASA Mars Trek | Mapa base, contexto regional y exploración visual | Las imágenes no sustituyen a un DEM |
| USGS Astrogeology | Geología, unidades del terreno y productos cartográficos | Debe conservarse la referencia del producto usado |
| Ruta propuesta de Curiosity | Contexto de navegación y comparación histórica | No es automáticamente una ruta transitable para humanos |
| NASA Worldview | Consulta de productos compatibles, solo si se valida que representan Marte | No se asumirán condiciones actuales de superficie |
| Imágenes de Perseverance | Evidencia visual y contexto de puntos científicos | Una imagen no es una medición topográfica |
| MOLA, HRSC, HiRISE y CTX | Elevación, relieve e imágenes regionales para la zona seleccionada | Hay que documentar resolución y cobertura |

Cada capa debe mostrar su fuente, producto, misión, resolución, cobertura, fecha o versión, sistema de coordenadas y tipo de dato. Las capas simuladas deben estar marcadas de forma visible.

## 7. Cómo se construye una ruta

La navegación se calculará sobre una cuadrícula. Cada celda tendrá, como mínimo:

- Elevación.
- Pendiente.
- Estado de transitabilidad.
- Riesgo o penalización.
- Interés científico opcional.

El coste de pasar de una celda a otra debe considerar la distancia, la pendiente, el riesgo y las restricciones. Un modelo inicial puede ser:

```text
coste_movimiento = distancia
                 × (1 + pesoPendiente × penalizaciónPendiente)
                 + pesoRiesgo × riesgo
                 + penalizaciónExclusión
                 - bonificaciónCientífica
```

Las celdas no transitables deben bloquearse, no recibir simplemente un coste alto. La heurística de A* debe ser admisible: distancia restante multiplicada por el coste mínimo posible por unidad de distancia.

Para una ruta científica, los objetivos se ordenarán y se resolverán como tramos: origen → objetivo 1 → objetivo 2 → destino. La aplicación debe indicar que esta estrategia es una aproximación y no un solucionador exacto del problema del viajante.

## 8. Resultado que debe ver el usuario

Después de calcular una misión, el usuario debe poder ver:

- La polilínea de cada ruta sobre el mapa.
- El perfil de elevación.
- Distancia total y desnivel acumulado.
- Tiempo estimado según la velocidad configurada.
- Pendiente máxima y pendiente media.
- Riesgo total y segmentos críticos.
- Objetivos científicos visitados.
- Supuestos y fuentes utilizados.
- Motivo por el que la ruta fue seleccionada.

Si no existe una ruta válida, la interfaz debe explicar el motivo y sugerir cambios seguros, como ampliar el área, reducir la pendiente máxima o quitar un objetivo inaccesible.

## 9. Restricciones técnicas

La aplicación será frontend-only:

- React, TypeScript y Vite.
- Leaflet para el mapa 2D.
- JSON y archivos locales para metadatos, puntos y peligros.
- Web Worker si el cálculo de A* bloquea la interfaz.
- `localStorage` para guardar misiones del usuario.
- Sin backend propio, base de datos, autenticación ni servidor Python.

Node.js se utilizará únicamente como entorno de desarrollo de Vite y las herramientas del frontend.

## 10. Prioridad de implementación

El orden recomendado es:

1. Datos locales consistentes y metadatos verificables.
2. Mapa 2D con capas y selección de coordenadas.
3. Cuadrícula de terreno, pendiente y transitabilidad.
4. Motor A* con una primera ruta válida.
5. Perfiles segura, rápida, científica y equilibrada.
6. Comparación, métricas y explicación de rutas.
7. Guardado y reporte de misión.
8. Mejoras visuales y exploración 3D.

La demostración principal debe ser: **seleccionar dos puntos, calcular varias rutas, compararlas y entender por qué una es la mejor para la misión**.
